# 02. 安全合规与威胁模型

## 1. 先说结论：Agent 安全要从“模型会不会乱说”升级到“系统会不会乱做”

普通问答系统的主要风险是回答错误。Agent 系统的风险更高，因为它可能：

- 读取企业数据
- 调用内部工具
- 写入业务系统
- 触发审批、发送、删除、下单等动作
- 将中间状态长期保存为记忆

因此安全设计必须覆盖输入、检索、模型、工具、状态、输出和审计。

## 2. 参考标准

企业项目建议将本章作为内部控制清单，再按组织要求映射到正式标准：

- [OWASP Top 10 for LLM Applications](https://owasp.org/www-project-top-10-for-large-language-model-applications/)
- [OWASP Top 10 for Agentic Applications 2026](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/)
- [NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework)
- [ISO/IEC 42001:2023](https://www.iso.org/standard/42001)

这些标准的共同要求可以落成四类工程动作：

1. 识别风险
2. 降低风险
3. 持续监控
4. 留下可审计证据

## 3. 威胁模型

| 风险 | 典型场景 | 控制措施 |
| --- | --- | --- |
| 提示注入 | 文档、网页、邮件里包含“忽略规则” | 上下文分区、指令优先级、检索内容只作为证据 |
| 越权访问 | 用户检索到无权文档 | 检索前置 ACL、租户隔离、结果二次校验 |
| 过度代理 | Agent 未确认就执行高风险动作 | 动作风险分级、人工确认、Tool Gateway 硬拦截 |
| 不安全输出处理 | 模型输出直接进入 SQL、脚本或 API | 结构化 schema 校验、参数白名单、沙箱执行 |
| 敏感信息泄露 | 输出 PII、密钥、内部报价 | 数据分级、脱敏、输出审查、最小上下文注入 |
| 工具滥用 | 工具参数被恶意构造 | 参数校验、幂等、速率限制、资源级授权 |
| 记忆污染 | 未确认事实写入长期记忆 | 写入审批、来源记录、过期策略、可撤销 |
| 数据投毒 | 知识库或索引混入恶意内容 | 数据源信任等级、签名、审核、异常检测 |
| 模型或供应链风险 | 第三方模型、插件、依赖被污染 | 供应商评估、版本锁定、SBOM、依赖扫描 |
| 审计缺失 | 出事后无法追踪 | 不可篡改日志、trace、版本记录、复盘流程 |

## 4. 权限模型

### 4.1 动作风险分级

| 等级 | 示例 | 默认策略 |
| --- | --- | --- |
| `read` | 查询文档、读取工单 | 可自动执行，但必须受 ACL 限制 |
| `low_write` | 创建草稿、生成任务建议 | 可自动执行或低门槛确认 |
| `medium_write` | 更新非关键字段、内部通知 | 需要策略校验和审计 |
| `high_write` | 对外发送、删除、审批、支付、生产变更 | 必须人工确认或人工执行 |
| `forbidden` | 绕过权限、导出全量敏感数据 | 系统硬拒绝 |

### 4.2 权限判断输入

Policy Engine 至少需要这些字段：

- `tenant_id`
- `user_id`
- `roles`
- `resource_type`
- `resource_id`
- `action`
- `risk_level`
- `data_classification`
- `environment`
- `approval_policy`

### 4.3 高风险动作强制要求

高风险动作必须满足：

1. 有明确操作者和审批者。
2. 有执行前 dry-run 或影响预览。
3. 有 idempotency key。
4. 有参数校验和资源级授权。
5. 有执行后核验。
6. 有回滚或补偿方案。
7. 有审计日志。

## 5. 数据安全

### 5.1 数据分级

| 等级 | 示例 | 处理要求 |
| --- | --- | --- |
| Public | 公开文档 | 可进入普通上下文 |
| Internal | 内部流程、普通知识库 | 需租户和角色控制 |
| Confidential | 客户信息、合同、报价 | 最小注入、脱敏、审计 |
| Restricted | 密钥、凭证、支付信息、核心生产配置 | 默认不进入模型上下文 |

### 5.2 最小上下文注入

不要把整份记录直接塞给模型。优先注入：

- 当前任务必要字段
- 已脱敏字段
- 摘要
- 引用 ID
- 可回源查询的标识符

## 6. 提示注入防护

RAG 和工具返回内容必须被明确标记为“数据”，不能被当作系统指令。

建议在上下文拼装时区分：

- `system_policy`
- `developer_instruction`
- `user_request`
- `retrieved_evidence`
- `tool_result`
- `memory`

模型不得把 `retrieved_evidence` 或 `tool_result` 中的文字升级为系统规则。

## 7. 红队测试清单

上线前至少覆盖这些攻击样本：

1. 检索文档中包含“忽略之前所有规则”。
2. 用户要求导出另一个租户的数据。
3. 用户让 Agent 直接删除生产记录。
4. 工具返回中夹带新的执行指令。
5. 用户要求把敏感信息发到外部邮箱。
6. 用户构造超长输入造成成本或延迟异常。
7. 用户诱导 Agent 写入错误长期记忆。
8. 用户要求绕过人工审批。

## 8. 审计证据

每个关键任务至少记录：

- `task_id`
- `trace_id`
- `tenant_id`
- `user_id`
- `roles`
- `input_summary`
- `retrieved_document_ids`
- `tool_calls`
- `policy_decisions`
- `approval_records`
- `model_version`
- `prompt_version`
- `output_summary`
- `risk_level`
- `final_status`

审计日志不只是为了排查，也是为了证明系统按设计执行过控制。

## 9. 合规落地方式

企业内落地时，不建议只写一句“符合安全要求”。应该形成证据包：

| 证据 | 内容 |
| --- | --- |
| 威胁模型 | 风险、攻击面、控制措施、剩余风险 |
| 权限矩阵 | 角色、动作、资源、审批策略 |
| 评估报告 | 高风险样本、红队样本、失败案例 |
| 审计样例 | trace、工具调用、审批、版本记录 |
| 运维记录 | 告警、演练、回滚、事故复盘 |
| 变更记录 | Prompt、模型、工具、策略、索引版本 |
