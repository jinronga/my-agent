# 04. SLO 与 Runbook

## 1. 先说结论：没有 SLO 和 Runbook 的 Agent，只是“能跑”，不是“可运营”

企业级 Agent 上线后，团队必须能回答：

- 多快算正常？
- 多慢要告警？
- 错到什么程度必须回滚？
- 哪些错误需要人工接管？
- 值班同学如何定位问题？
- 事故后如何复盘和补评估样本？

这些问题要在上线前写清楚。

## 2. 推荐 SLI

| 类型 | SLI |
| --- | --- |
| 可用性 | API 成功率、任务完成率 |
| 延迟 | API p50/p95/p99、工具调用 p95、模型调用 p95 |
| 质量 | 任务成功率、引用命中率、拒答正确率 |
| 安全 | 越权拦截数、关键错误数、高风险动作未确认数 |
| 成本 | 单任务 token、单任务模型成本、工具调用次数 |
| 数据 | 数据源同步延迟、索引新鲜度、embedding 队列积压 |

## 3. 推荐 SLO

可以按场景设不同目标。内部知识问答的基线可以是：

| 指标 | 目标 |
| --- | --- |
| API 月可用性 | >= 99.5% |
| `/v1/query` p95 | <= 5s |
| 检索 p95 | <= 800ms |
| 生成 p95 | <= 4s |
| 索引新鲜度 | 核心知识源 <= 15min |
| 关键错误率 | 0 |
| 越权回答 | 0 |
| 审计日志完整率 | >= 99.9% |

如果是代码辅助、客服辅助、合规审查，SLO 应按业务 SLA 单独定义。

## 4. 告警规则

| 告警 | 触发条件 | 优先级 |
| --- | --- | --- |
| 关键错误 | 高风险动作未确认执行 | P0 |
| 越权风险 | 检索或输出命中越权告警 | P0 |
| 服务不可用 | API 错误率持续升高 | P1 |
| 延迟异常 | p95 超阈值持续 10 分钟 | P1 |
| 成本异常 | 单任务成本超过预算 2 倍 | P1 |
| 索引滞后 | 核心数据源超过新鲜度 SLA | P1 |
| 引用缺失 | 引用缺失率异常升高 | P2 |
| 无结果率异常 | 无结果率超过历史均值阈值 | P2 |

## 5. Runbook：服务错误率升高

1. 查看 API Gateway 错误率，确认影响租户和接口。
2. 按 trace 抽样查看失败点：
   - 鉴权失败
   - Retrieval 失败
   - Model Gateway 超时
   - Tool Gateway 失败
   - Policy Engine 拒绝
3. 查看最近变更：
   - prompt
   - model
   - retrieval config
   - policy
   - index alias
4. 如果是新版本引起，切回上一稳定版本。
5. 保存失败 trace，回流到 regression 评估集。

## 6. Runbook：越权或敏感信息风险

1. 立即冻结相关租户或场景的自动回答。
2. 保留请求、检索结果、模型输出、权限判断和审计日志。
3. 确认是检索前 ACL 缺失、生成层泄露，还是工具返回泄露。
4. 如果影响真实用户，按企业安全事件流程升级。
5. 修复后必须补充安全回归样本。
6. 未通过安全回归前不得重新放量。

## 7. Runbook：模型质量回退

1. 对比当前版本和上一生产版本的评估报告。
2. 查看失败样本是否集中在某个场景、工具或数据源。
3. 检查 prompt、模型、rerank、上下文打包是否变更。
4. 若回退影响核心场景，回滚 prompt 或模型路由。
5. 将线上失败样本加入 regression。

## 8. Runbook：成本异常

1. 查看单任务平均 token、最大 token、工具调用次数。
2. 定位是否存在循环调用、过度检索、上下文过长。
3. 临时降低最大步数、top-k、上下文窗口或模型档位。
4. 对异常用户、租户或场景做限流。
5. 修复后补充成本预算测试。

## 10. 演练要求

至少每季度演练：

- prompt 回滚
- 模型路由回滚
- 索引 alias 回滚
- 高风险动作拦截
- 审计日志查询
- 安全样本回归

没有演练过的回滚流程，不能假设它真的可用。
