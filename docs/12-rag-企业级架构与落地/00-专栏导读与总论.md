# 00. 专栏导读与总论

## 1. 先说结论：企业级 RAG 的真正难点，从来都不只是“怎么检索”，而是怎么把知识、权限、流程和系统边界一起做对

如果只看公开演示，  
RAG 很容易被理解成这样一件事：

> 把文档切片，做 embedding，放进向量库，  
> 再接一个大模型回答问题。

这个理解不能说错，  
但它通常只够支撑一个 demo。

真正到了企业环境，  
RAG 很快会变成另一类问题：

- 文档不只在一个知识库里，而是散在 CRM、ERP、Wiki、Git、邮件、工单、审批系统
- 不同用户看到的数据范围不一样，权限和租户边界不能错
- 很多问题不是“找文档”，而是“结合最新系统状态给出结论”
- 很多场景不是“回答一下”，而是“回答后要不要进一步调用系统动作”
- 线上一旦回答旧内容、错内容、越权内容，代价并不低

所以这套专栏最重要的出发点不是介绍一个“能跑通的 RAG 样板”，  
而是系统回答下面这个问题：

> **企业级 RAG 到底应该怎么设计，怎么选型，怎么接入现有系统，怎么上线，怎么治理，怎么长期运维？**

## 2. 这套专栏解决的是什么问题

这套材料主要解决四类常见问题。

### 2.1 架构层的问题

- 企业级 RAG 应该怎么分层？
- `ingestion`、`retrieval`、`generation`、`agent orchestration` 的边界怎么定？
- 离线链路和在线链路该怎么拆？

### 2.2 选型层的问题

- 向量数据库是不是必须？
- 如果不是，还有哪些替代路径？
- Elasticsearch、RedisSearch、全文检索 + 重排序、数据库插件、内存索引分别适合什么？

### 2.3 落地层的问题

- 怎么接 CRM、ERP、知识库、代码仓库？
- 怎么同时处理知识类内容和实时状态类内容？
- 哪些场景只需要 RAG，哪些场景要升级到 Agent？

### 2.4 治理层的问题

- 数据写入和更新怎么做？
- 版本、权限、监控、备份、回滚怎么设计？
- RedisSearch 如果作为向量或混合检索层，企业级维护要做哪些事？

## 3. 为什么今天的企业项目里，RAG 经常被做偏

我见过很多项目在立项时会先讨论：

- 选哪个 embedding 模型
- 选哪个向量数据库
- top-k 设多少
- prompt 怎么写

这些当然都重要，  
但它们很容易让团队把注意力过早集中在“模型和检索技术”上，  
而忽略了真正决定成败的部分：

- 数据源是不是完整
- 权限是不是前置
- 删除和更新是不是能传播
- 检索和回源边界是不是清楚
- 线上效果是不是可评估、可回滚

结果就是：

- demo 看起来不错
- 但一接真实系统就开始出现脏数据、旧数据、越权、延迟和成本问题

所以这套专栏会反复强调一个核心判断：

**企业级 RAG 首先是一项数据与系统工程，其次才是一项模型应用工程。**

## 4. 这套专栏的目标读者

这套内容主要适合四类读者：

### 4.1 技术负责人 / 架构师

你需要回答：

- 值不值得做
- 怎么立项
- 技术路线怎么定
- 风险和投入怎么控制

### 4.2 后端 / 平台工程师

你需要落地：

- 数据接入
- 索引构建
- 查询服务
- 版本与运维

### 4.3 AI 应用工程师

你更关注：

- 检索和生成怎么配合
- 什么场景应该升级到 Agent
- 怎么做引用、拒答和结构化输出

### 4.4 业务系统负责人

你更关心：

- 现有 CRM、ERP、知识库要怎么接
- 数据权限能不能守住
- 真实业务痛点能不能被解决

## 5. 这套专栏的主线，不是“工具大全”，而是一套决策框架

整套内容会围绕下面 8 个关键判断展开。

### 5.1 企业级 RAG 先是一个数据系统

如果数据接入、清洗、版本和权限不稳，  
后面的模型效果通常也不稳。

### 5.2 向量数据库不是前提

很多问题用全文检索、结构化查询或混合检索更合理。

### 5.3 离线生产链路和在线查询链路要拆开

否则系统一复杂，就会互相拖累。

### 5.4 检索层和生成层要分开优化

“找对”和“说清楚”是两件不同的事情。

### 5.5 权限要前置

企业级 RAG 不是公共搜索，  
能不能查、能查到什么，必须在检索阶段尽量控制。

### 5.6 很多问题不该直接走 Agent

如果只是查知识、做摘要、给引用，  
没必要上来就做多步编排。

### 5.7 RedisSearch 很强，但有边界

它适合低延迟热数据检索，  
但不是所有企业知识的唯一底座。

### 5.8 没有治理，RAG 很难长期活下去

版本、回滚、监控、评估、索引重建，  
这些不是“后面再补”的内容。

## 7. 这套专栏默认采用哪些统一口径

为了避免前后表达漂移，  
这里统一几组核心术语。

### 7.1 `RAG`

默认指：

> 检索外部知识或外部上下文后，再让模型基于这些上下文完成回答、摘要、判断或下一步决策建议。

这里的外部知识既可能是文档，  
也可能是结构化数据、规则条款、代码上下文或业务记录。

### 7.2 `企业级 RAG`

默认强调以下几个特征：

- 连接企业现有系统
- 存在权限和租户边界
- 有版本、回滚、监控和治理要求
- 不是只服务单次 demo

### 7.3 `向量数据库`

默认指以向量索引和近邻检索为核心能力的数据系统。  
但这套专栏不会把它默认视为企业级 RAG 的唯一基础设施。

### 7.4 `混合检索`

默认指：

- 全文检索
- 向量检索
- 标签 / 字段过滤
- rerank

等策略的组合。

### 7.5 `Agent orchestration`

默认指：

> 在检索之外，还需要做任务编排、工具调用、人机确认和多步执行时的控制层。

不是所有 RAG 都需要它。

## 8. 我最想通过这套专栏传达的一句话

如果你只记住一句话，  
我希望是这句：

> 企业级 RAG 的关键，不是先把“向量检索”做出来，  
> 而是先把“知识来源、权限边界、检索路径、生成约束和运维治理”一起设计清楚。

## 9. 小结

- 这套专栏关注的是企业级、生产级、可治理的 RAG
- 核心主线是架构、选型、集成、实践和运维，而不是单点技巧
- 向量数据库很重要，但不是问题的起点
- 真正可落地的 RAG，一定是系统工程，不只是模型工程
