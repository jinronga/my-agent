# 01. 企业级 RAG 总体建设方案

## 1. 建设目标

本方案的目标，是在企业现有系统基础上建设一套 **可接入、可检索、可生成、可治理、可演进** 的企业级 RAG 能力平台，支撑以下典型场景：

- 客服问答辅助
- 代码辅助与知识检索
- 文档检索与制度问答
- 合规审查辅助

目标不是建设一个单点问答机器人，  
而是沉淀一套可被多个业务复用的知识增强底座。

## 2. 先说结论：建议采用“离线知识生产 + 在线检索生成 + 可选 Agent 编排 + 治理平面”四层架构

推荐建设路径如下：

1. 先建设统一接入和离线知识生产链路
2. 再建设统一检索与生成服务
3. 再按业务需要引入 Agent orchestration
4. 同步建设版本、权限、评估、监控和重建体系

这样做的原因是：

- 先解决知识接入和索引可用性
- 再解决问答质量和场景适配
- 最后再引入跨系统动作，控制复杂度和风险

## 3. 总体架构

### 3.1 离线层

负责：

- 连接 CRM、ERP、知识库、Git、工单系统
- 规范化和清洗
- chunk 切分
- embedding
- 构建全文 / 向量 / 混合索引
- 版本发布

### 3.2 在线层

负责：

- Query 理解
- 检索路由
- 过滤与重排序
- 基于证据的生成
- 引用和结构化输出

### 3.3 Agent 层

仅在以下场景启用：

- 检索后还需要进一步调用系统动作
- 需要多步任务编排
- 需要审批或人工确认

### 3.4 治理层

负责：

- 版本管理
- 权限隔离
- 可观测性
- 评估与回归
- 备份恢复
- 索引重建

## 4. 核心模块职责

### 4.1 Ingestion

负责把源系统内容转成可检索资产。

### 4.2 Retrieval

负责把用户问题转成合适的召回和排序策略。

### 4.3 Generation

负责把召回内容组织成带引用、可控、可消费的结果。

### 4.4 Agent Orchestration

负责多步执行、工具调用和人工确认。

## 5. 与企业现有系统的集成策略

### 5.1 知识类系统

例如：

- 企业 Wiki
- 制度库
- FAQ
- 产品文档

建议采用：

- 全量镜像 + 增量同步
- 离线索引

### 5.2 业务状态类系统

例如：

- CRM
- ERP
- 工单系统
- 审批系统

建议采用：

- 检索知识
- 查询时回源获取最新状态

### 5.3 代码和工程资产

建议：

- 文件、类、函数分层索引
- symbol / path 检索和语义召回组合

## 6. 技术路线建议

### 6.1 主语言

- `Go`

### 6.2 基础设施建议

- API 层：Go
- Worker 层：Go
- 元数据：PostgreSQL
- 对象存储：S3 / MinIO
- 消息队列：Kafka / NATS / Redis Streams
- 检索层：按业务选择 RedisSearch、Elasticsearch 或 PostgreSQL + `pgvector`

### 6.3 关于向量数据库的决策建议

不建议把“是否上向量数据库”当作立项前提。

建议按照以下顺序决策：

1. 判断问题是关键词型、语义型还是结构化型
2. 判断是否已有成熟搜索栈可复用
3. 判断权限和过滤复杂度
4. 判断是否真的需要独立向量系统

## 7. RedisSearch 方案建议

如果项目重点是：

- 低延迟
- 热数据
- 混合检索
- Go 服务快速集成

可以优先考虑 RedisSearch 作为在线检索层。

建议前提：

- 保留对象存储和元数据数据库作为事实来源
- 索引内置版本字段
- 前置 ACL 过滤
- 使用 alias 做版本切换

## 8. 分阶段实施路线

### 8.1 阶段一：建设统一知识接入与检索能力

目标：

- 接入 1 到 2 个核心知识源
- 完成检索和引用式回答
- 建立最基本权限模型

### 8.2 阶段二：扩展到多业务场景

目标：

- 接入 CRM / ERP 等业务系统
- 支持知识 + 实时状态联合回答
- 建立评估集和监控指标

### 8.3 阶段三：引入 Agent 能力

目标：

- 把部分场景从“回答”升级到“回答 + 动作建议 / 执行”
- 建立审批和人工确认

### 8.4 阶段四：平台化和治理深化

目标：

- 版本管理
- 统一配置
- 重建和回滚
- 容量规划

## 9. 预期收益

### 9.1 业务收益

- 缩短客服和支持响应时间
- 缩短研发定位和复用时间
- 提升制度和文档检索效率
- 提升合规审查辅助效率

### 9.2 技术收益

- 把分散知识沉淀为统一可复用能力
- 降低重复接入和重复问答系统建设成本
- 为后续 Agent 化奠定统一底座

## 10. 主要风险与控制策略

| 风险 | 说明 | 控制策略 |
| --- | --- | --- |
| 数据不完整 | 接入源覆盖不足 | 先做数据盘点和分阶段接入 |
| 权限风险 | 越权检索或回答 | 检索前置 ACL，审计日志 |
| 数据过期 | 索引滞后于源系统 | 事件驱动同步和新鲜度监控 |
| 效果不稳定 | 检索或生成波动 | 建评估集、版本化配置、回放测试 |
| 运维复杂度上升 | 新增搜索与模型链路 | 复用现有基础设施，分阶段建设 |

## 11. 建议决策

建议立项时不要直接以“搭一个问答机器人”作为目标，  
而应以“建设企业级知识增强底座”作为目标。

理由是：

- 它更适合长期演进
- 它能同时服务多个业务场景
- 它能逐步承接 Agent、自动化与智能流程能力

## 12. 小结

- 推荐采用四层架构：离线、在线、可选 Agent、治理
- 不建议从向量数据库出发定义方案
- RedisSearch 可以作为低延迟检索层，但要和版本、权限、重建配套
- 实施应按阶段推进，先做知识能力，再做动作能力
