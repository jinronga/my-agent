# 02. 实施路线图与里程碑

## 1. 先说结论：企业级 RAG 最稳的推进方式，不是一次性铺满，而是按“一个高价值场景验证 -> 多场景复用 -> 平台化治理”逐步推进

如果一开始就同时追求：

- 多业务线接入
- 多数据源统一
- 向量检索
- Agent 编排
- 自动执行动作

项目复杂度会迅速失控。

更稳的方式是分阶段推进，  
每一阶段都必须有明确可验证的交付结果。

## 2. 推荐的四阶段路线图

## 2.1 第一阶段：MVP 验证

### 目标

- 跑通一个高价值业务场景
- 接入 1 到 2 个核心知识源
- 支持带引用的检索式回答

### 建议场景

- 客服 FAQ 辅助
- 内部知识库问答
- 单仓库代码检索

### 交付物

- 最小 query API
- 最小 ingestion worker
- 基础索引和引用式回答
- 基础权限过滤

### 成功标准

- 能稳定回答真实问题
- 有可接受的延迟
- 能返回明确引用来源

## 2.2 第二阶段：场景扩展

### 目标

- 扩展到 2 到 3 个业务场景
- 接入结构化系统和文档系统
- 支持混合检索

### 交付物

- 检索路由
- rerank
- 查询日志和评估集
- CRM / ERP / Wiki 的组合接入

### 成功标准

- 场景间可复用同一套底座
- 能处理知识 + 实时状态联合回答

## 2.3 第三阶段：Agent 化升级

### 目标

- 对部分高价值场景引入 Agent orchestration
- 支持多步决策、工具调用和人工确认

### 交付物

- 任务状态管理
- 工具权限控制
- 审批与人工确认节点
- 审计日志

### 成功标准

- 任务完成率明显优于纯问答
- 风险动作都能被控制和回溯

## 2.4 第四阶段：平台化与治理深化

### 目标

- 支持多团队复用
- 建立标准化治理能力

### 交付物

- 索引版本管理
- 备份恢复
- 重建流水线
- 容量规划
- 统一配置中心

### 成功标准

- 可支撑多业务线
- 故障可恢复
- 重建和回滚可演练

## 3. 建议的时间安排

### 3.1 0 到 4 周

- 明确场景
- 数据盘点
- 接入一个知识源
- 做第一版检索回答

### 3.2 4 到 8 周

- 补混合检索
- 接入实时状态回源
- 做评估和监控

### 3.3 8 到 12 周

- 扩第二个业务场景
- 做版本化和重建机制
- 形成统一服务接口

### 3.4 12 周以后

- 选择少量高价值场景做 Agent 升级
- 做平台化复用

## 4. 资源角色建议

建议至少包括：

- 1 名技术负责人 / 架构师
- 1 到 2 名 Go 后端 / 平台工程师
- 1 名 AI 应用工程师
- 1 名业务系统接口负责人
- 按需配置测试 / SRE / 运维支持

## 5. 每阶段的风险检查点

### 5.1 第一阶段

- 数据是否真的足够支撑场景
- 真实查询是否比想象中更复杂

### 5.2 第二阶段

- 混合检索是否真正提升效果
- 回源链路是否拖慢整体时延

### 5.3 第三阶段

- Agent 是否真的带来额外价值
- 动作权限是否可控

### 5.4 第四阶段

- 平台是否被多个团队接受
- 运维和治理能力是否跟上

## 6. 推荐的阶段评审问题

每次里程碑评审建议至少问：

1. 当前上线场景的真实收益是什么？
2. 主要失败样例是什么？
3. 权限和审计是否可证明？
4. 如果今天要重建索引，能否平滑完成？
5. 下一阶段增加的复杂度，是否真的有明确业务回报？

## 7. 小结

- 企业级 RAG 最稳的推进方式是按阶段做，而不是一次性铺满
- 先验证高价值场景，再做多场景复用，最后做 Agent 与平台化
- 每个阶段都必须有清晰交付物、成功标准和风险检查点
