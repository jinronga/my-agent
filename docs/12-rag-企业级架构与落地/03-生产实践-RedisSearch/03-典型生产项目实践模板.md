# 03. 典型生产项目实践模板

## 1. 先说结论：真实生产项目的重点不是“哪一层最先进”，而是整条链路能否稳定交付业务价值

企业里落 RAG，  
最终不会按“我们用了什么库”来验收，  
而是按这些问题来验收：

- 客服是否更快回答用户问题
- 研发是否更快定位代码和文档
- 合规是否更快拿到带依据的审查建议
- 运维是否能看见延迟、错答、更新滞后和权限异常

所以这一篇给出的不是“单点最佳实践”，  
而是一套更适合真实项目推进的生产模板。

## 2. 一个推荐的技术栈组合

以 `Go` 为主语言时，  
一套比较均衡的技术栈可以是：

- API 服务：`Go + Gin / Chi`
- 检索服务：`Go`
- Worker：`Go`
- 消息总线：Kafka / NATS / Redis Streams
- 元数据数据库：PostgreSQL
- 对象存储：MinIO / S3
- 向量与混合检索：RedisSearch
- 可观测性：Prometheus + Grafana + OpenTelemetry
- 模型接入：内部 LLM Gateway 或统一模型代理层

## 3. 生产项目模板一：客服问答辅助

### 3.1 业务痛点

- 客服知识更新快
- 问题口语化严重
- 回答需要结合订单状态和历史工单

### 3.2 推荐架构

- FAQ、SOP、产品知识离线入 RedisSearch
- 工单和订单状态查询时回源 CRM / 工单系统
- 先做检索问答
- 需要创建工单、退款、升级处理时再进入 Agent 编排

### 3.3 为什么这样设计

- 知识部分适合提前索引
- 状态部分必须实时
- 把“回答”和“执行动作”分开，更安全

### 3.4 关键指标

- 命中标准答案比例
- 生成答案附引用比例
- 人工坐席平均处理时长
- 高风险错误建议数

## 4. 生产项目模板二：代码辅助

### 4.1 业务痛点

- 仓库大，历史包袱重
- 代码和文档割裂
- 新人找不到已有实现

### 4.2 推荐架构

- 代码仓库解析成文件、类、函数三级索引
- README、设计文档、PR 描述单独建索引
- symbol 检索和全文检索作为第一召回
- 语义检索和 rerank 作为补充

### 4.3 为什么这样设计

- 代码问题经常带显式路径和 symbol
- 只做自然语言向量检索会漏掉关键实现

### 4.4 关键指标

- 正确文件命中率
- 采纳建议比例
- 误导性引用率
- 平均排障时间

## 5. 生产项目模板三：合规审查辅助

### 5.1 业务痛点

- 规则来源多
- 需要引用依据
- 错误成本高，必须有审计

### 5.2 推荐架构

- 制度和规则条款做全文检索主召回
- 历史案例库做语义补召回
- 生成层输出固定结构：
  - 结论
  - 引用条款
  - 风险等级
  - 待人工确认事项
- 高风险结果必须走人工复核

### 5.3 为什么这样设计

- 合规问题解释性优先于“回答自然”
- 规则型知识天然适合全文检索和条款匹配

### 5.4 关键指标

- 引用条款完整率
- 人工复核通过率
- 高风险漏报率
- 审计日志完备度

## 6. 一套推荐的生产推进节奏

### 6.1 第一步：只做“能回答”

完成：

- 单个业务域接入
- 可引用回答
- 最基本权限过滤

### 6.2 第二步：做“答得稳”

完成：

- 查询日志回放
- 检索评估集
- 失败案例归因
- prompt 和索引版本管理

### 6.3 第三步：做“能运营”

完成：

- 监控指标
- 备份恢复
- 索引重建
- 容量规划
- 回滚流程

### 6.4 第四步：做“能动作”

完成：

- Agent orchestration
- 工具调用
- 人机确认
- 安全策略

## 7. 真实项目里最该优先投入的工程点

1. **日志和可观测性**  
没有日志，无法定位是检索错了还是生成错了。

2. **权限模型**  
一旦越权，业务方信任会迅速下降。

3. **版本和回滚**  
没有版本，线上问题就很难回退。

4. **评估集**  
没有真实问题集，调优就只能靠主观感觉。

5. **回源能力**  
很多看似“知识问题”的请求，本质上还需要实时系统状态。

## 8. 一套更适合 Go 工程团队的项目拆分

- `cmd/query-api`：对外检索和问答入口
- `cmd/ingest-worker`：数据同步和处理
- `cmd/rebuild-job`：索引重建和切换
- `internal/connectors`：CRM、ERP、Wiki、Git 适配器
- `internal/retrieval`：查询路由、融合、rerank
- `internal/generation`：prompt 和模型封装
- `internal/orchestration`：Agent 任务编排

## 9. 小结

- 生产项目关注的是业务闭环，而不是单点技术炫技
- RedisSearch 很适合做在线召回层，但要和回源、治理、评估配套
- 最稳的推进方式是先问答，再稳定，再治理，最后再引入 Agent 动作能力
