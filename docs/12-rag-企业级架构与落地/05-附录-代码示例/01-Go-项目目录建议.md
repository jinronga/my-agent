# 01. Go 项目目录建议

## 1. 先说结论：企业级 RAG 的 Go 工程，建议按“在线服务 / 离线任务 / 公共能力”三层来组织

如果目录按“模型、数据库、工具函数”随意堆叠，  
随着 connector、检索策略、Agent 编排和运维作业增多，  
代码会很快失控。

更稳的组织方式通常是：

- `cmd/` 放可执行入口
- `internal/` 放业务实现
- `pkg/` 只放真正可复用的公共包

## 3. 为什么这样拆

### 3.1 `cmd/`

把不同运行角色拆开：

- 在线查询 API
- 离线 ingestion worker
- 索引重建作业
- 评估任务

### 3.2 `internal/connectors`

把源系统适配隔离开，  
避免 CRM、ERP、Wiki 的特殊逻辑散落到业务主流程里。

### 3.3 `internal/retrieval`

把全文、向量、混合、rerank、路由分层，  
后续替换实现会轻松很多。

### 3.4 `internal/orchestration`

只有需要 Agent 时才进入这里。  
普通问答不要和多步工具调用共用同一套复杂流程。

## 4. 推荐的接口放置方式

- 面向外部系统的接口定义，放在最小依赖的包里
- 具体实现放在各自的子目录
- 避免在 `cmd/` 里写业务逻辑

## 5. 小结

- Go 工程结构的关键是把在线、离线和治理分层
- 目录边界清晰后，RAG 项目更容易持续演进
