# 03. 真实业务场景映射

## 1. 先说结论：同样叫 RAG，不同业务场景的最佳做法差别很大

很多技术讨论容易抽象到：

- 检索准确率高不高
- 用不用向量数据库
- 大模型回答好不好

但真实生产项目是按业务问题付费的。  
所以更有价值的问法是：

- 它解决的是哪种业务痛点？
- 错误答案会造成什么后果？
- 用户更看重召回率、可解释性，还是实时性？

本篇把常见企业场景拆成四类，  
分别给出更适合的架构组合。

## 2. 客服问答

### 2.1 典型业务痛点

- 客服培训周期长
- FAQ 和工单经验分散
- 用户问题描述口语化、改写多
- 回答需要结合订单和工单当前状态

### 2.2 推荐方案

- FAQ、产品知识、SOP：离线索引
- 工单状态、订单状态：查询时回源
- 召回策略：全文检索 + 语义召回 + rerank
- 生成策略：必须返回引用和建议操作步骤

### 2.3 更适合的技术组合

- 检索：RedisSearch 或 Elasticsearch
- 实时状态：CRM / 工单系统 API
- 编排：仅在需要提交工单、发起退款等动作时启用 Agent

### 2.4 核心指标

- 首问解决率
- 引用覆盖率
- 人工转接率
- 错答投诉率

## 3. 代码辅助

### 3.1 典型业务痛点

- 新人难以理解仓库结构
- 历史实现分散，复用困难
- 问题既包含自然语言，也包含 symbol、路径、错误日志

### 3.2 推荐方案

- 代码 symbol、路径、文件名：优先精确索引
- 函数注释、设计文档、PR 说明：适合语义索引
- 检索单元：文件、类、函数、方法、README 分开建模

### 3.3 更适合的技术组合

- 初召回：全文 / symbol 检索
- 二次召回：embedding 或 code reranker
- 生成：限制上下文窗口，强制返回文件路径和代码片段引用

### 3.4 核心指标

- 命中正确仓库 / 模块的比例
- 建议代码被采纳率
- 误导性建议率
- 平均定位时间

## 4. 文档检索

### 4.1 典型业务痛点

- 文档多，找不到最新版本
- 同一主题分散在多个系统
- 查询者不确定准确关键词

### 4.2 推荐方案

- 标题、目录、标签、更新时间作为强元数据
- 先做全文和标签过滤，再补语义召回
- 答案必须显示来源、文档空间、最后更新时间

### 4.3 更适合的技术组合

- 检索：Elasticsearch / OpenSearch
- rerank：cross-encoder 或 LLM rerank
- 生成：以摘要和引用为主，而不是长篇自由发挥

### 4.4 核心指标

- 最新文档命中率
- 无结果率
- 用户二跳点击率
- 查询后再次搜索率

## 5. 合规审查

### 5.1 典型业务痛点

- 条款分散在制度、法务意见、历史案例中
- 问题需要引用依据，不能只给自然语言结论
- 错误成本高，必须可审计

### 5.2 推荐方案

- 制度条款和历史案例分库建索引
- 规则库优先全文和字段检索
- 案例库可补语义检索
- 生成层必须输出“结论 + 依据 + 不确定项”

### 5.3 更适合的技术组合

- 检索：全文检索 + 标签过滤 + 案例 rerank
- 生成：结构化 JSON 或固定模板
- 编排：引入人工确认节点，不直接自动执行高风险动作

### 5.4 核心指标

- 依据引用完整率
- 审查一致性
- 人工复核通过率
- 高风险误判率

## 6. 场景和方案的对应关系

| 业务场景 | 主问题类型 | 主检索方式 | 是否需要回源 | 是否适合 Agent |
| --- | --- | --- | --- | --- |
| 客服问答 | FAQ + 状态混合 | 混合检索 | 需要 | 条件满足时适合 |
| 代码辅助 | symbol + 语义混合 | 精确检索 + rerank | 一般不需要 | 多步骤修改时适合 |
| 文档检索 | 文档定位和摘要 | 全文 / 混合检索 | 偶尔需要 | 多数情况下不必 |
| 合规审查 | 规则匹配 + 证据引用 | 全文 + 案例检索 | 可能需要 | 只适合做辅助，不适合直接决策 |

## 7. 一个统一的场景判断框架

落地前建议每个场景都回答下面 6 个问题：

1. 用户是要“找文档”，还是要“拿结论”，还是要“让系统做动作”？
2. 数据是静态知识还是动态状态？
3. 错误答案最坏会导致什么？
4. 是否需要明确引用和审计？
5. 是否存在复杂权限或租户隔离？
6. 是否真的需要 Agent，而不是普通检索问答？

## 8. 小结

- 场景不同，最优方案差别很大
- 客服、代码、文档、合规四类场景不应该共用一套完全相同的索引策略
- 先按业务痛点拆场景，再决定检索、生成和 Agent 的边界，项目会稳很多
