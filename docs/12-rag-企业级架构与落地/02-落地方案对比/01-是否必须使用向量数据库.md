# 01. 是否必须使用向量数据库

## 1. 先说结论：不必须，向量数据库只是企业级 RAG 的一种实现，不是前提条件

这个问题之所以常见，  
是因为很多 RAG 入门文章默认采用下面这条路径：

> 文档切片 -> embedding -> 向量数据库 -> 相似度检索 -> 大模型回答

这条路径在 demo 和很多语义检索场景里都有效。  
但企业环境里，真正决定方案的往往不是“能不能做 embedding”，而是：

- 数据主要是语义型，还是关键词 / 字段型？
- 权限过滤是不是复杂？
- 更新频率高不高？
- 团队有没有额外维护新型基础设施的能力？
- 是否需要全文检索、标签过滤、结构化查询混用？

所以更准确的说法应该是：

**企业级 RAG 需要的是“可用的检索层”，而不是“必须叫向量数据库的东西”。**

## 2. 哪些情况下不用专门向量数据库也能做好 RAG

### 2.1 问题本身关键词很强

例如：

- 制度条款号查询
- 错误码查询
- API 名称查询
- 合同模板字段查询

这类问题里，  
关键词和字段过滤往往比纯语义相似更可靠。

### 2.2 数据天然结构化

例如：

- CRM 里的客户字段
- ERP 里的订单、审批、付款记录
- 项目管理系统里的工单状态

这类数据通常更适合：

- SQL 查询
- 搜索引擎字段检索
- 查询时回源

### 2.3 语料规模并不大

如果只有几万到几十万 chunk，  
而且并发不高，往往可以先用：

- PostgreSQL + `pgvector`
- Elasticsearch / OpenSearch
- RedisSearch
- 内存 HNSW

没必要第一天就引入新的独立向量数据库集群。

### 2.4 团队更擅长现有搜索或数据库栈

如果团队已经长期维护：

- Elasticsearch
- PostgreSQL
- Redis

那优先复用熟悉的技术栈，  
通常比引入一套全新向量库更稳。

## 3. 常见替代方案

### 3.1 Elasticsearch / OpenSearch 稠密向量 + 稀疏向量

适合：

- 已有搜索平台
- 需要全文、过滤、聚合和语义检索并存
- 需要较成熟的运维体系

优点：

- 稠密 / 稀疏 / 全文三类检索能力可以统一
- 过滤能力强
- 生态成熟，日志和搜索团队普遍熟悉

缺点：

- 索引和集群调优复杂
- 大规模向量召回的成本不一定最低

### 3.2 全文检索 + 重排序

适合：

- 文档结构规整
- 关键词命中比语义近邻更关键
- 想快速上线第一版

做法：

- 先用 BM25 / 倒排索引召回一批候选
- 再用 cross-encoder 或大模型 rerank

优点：

- 效果往往比“裸向量检索”更稳
- 权限、过滤、解释性都更容易做

缺点：

- 对纯语义改写类问题召回可能不足

### 3.3 传统数据库 + embedding 插件

典型例子：

- PostgreSQL + `pgvector`
- SQLite + 向量扩展

适合：

- 中小规模语料
- 强事务一致性
- 想把元数据和向量放在一个系统里

优点：

- 工程栈简单
- 数据一致性容易保证
- 便于和业务库联动

缺点：

- 纯向量检索性能上限不如专门搜索引擎或专门向量库

### 3.4 RedisSearch

适合：

- 低延迟在线检索
- 热数据
- 向量 + 标签 + 全文混合过滤
- Go 服务快速集成

优点：

- 延迟低
- 读写都快
- 适合中等规模在线服务

缺点：

- 长期海量知识底座和复杂离线分析不是它的强项
- 内存成本需要严格评估

### 3.5 内存向量索引

典型例子：

- HNSW
- FAISS

适合：

- 单租户小型知识集
- 本地代码辅助
- 边缘部署
- 实验环境

优点：

- 非常快
- 系统简单

缺点：

- 持久化、权限、备份、共享访问都需要额外补

## 4. 什么时候向量数据库是合理选择

如果同时满足下面几条，  
向量数据库或强向量能力的搜索系统就比较合适：

1. **问题以语义相似和近义改写为主**
2. **数据规模已经超出单机内存或普通数据库舒适区**
3. **需要高并发低延迟召回**
4. **团队能承担索引构建、容量规划和监控运维**
5. **权限过滤、版本切换和回滚方案已经设计清楚**

## 5. 一个更实用的决策顺序

不要先问：

> 我们用不用向量数据库？

更建议先按下面顺序问：

1. 用户问题更像“关键词查找”还是“语义理解”？
2. 数据是静态知识还是高频变化状态？
3. 结果是否必须按租户 / 角色 / 组织过滤？
4. 召回后是否还会做 rerank？
5. 团队是否已经有稳定的 Elasticsearch / PostgreSQL / Redis 基础设施？

## 6. 推荐的落地顺序

### 6.1 第一阶段：先做能稳定上线的检索层

优先考虑：

- 全文检索 + 元数据过滤
- 必要时再加 rerank

### 6.2 第二阶段：在真正需要的语义场景里补向量检索

优先补充：

- FAQ 改写
- 相似案例检索
- 复杂自然语言问法

### 6.3 第三阶段：做混合检索和路由

这时再决定是否：

- 引入 RedisSearch
- 迁移到 Elasticsearch 稠密 / 稀疏混合
- 保持 PostgreSQL + rerank 方案

## 7. 常见误区

### 7.1 把“有 embedding”误认为“必须有向量数据库”

很多系统完全可以：

- 把 embedding 存在 PostgreSQL
- 用全文检索召回候选
- 用 embedding 或 reranker 做二次排序

### 7.2 一上来把所有数据统一向量化

财务状态字段、审批节点、代码 symbol 名称，  
很多都不该被等价看成自然语言段落。

### 7.3 只比较检索效果，不比较治理成本

在企业里，  
权限、版本、回滚、备份和监控通常和检索精度同样重要。

## 8. 小结

- 向量数据库不是企业级 RAG 的必答题
- 真正该选的是“适合业务约束的检索架构”
- 很多团队的更优起点是全文检索、数据库插件或现有搜索栈
- 只有在语义召回收益明确时，再把向量能力引入主链路
